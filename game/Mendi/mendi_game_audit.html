Bugs — code that breaks or crashes
Bug
logBoxEl is always null — game-log references a missing element
logBoxEl is assigned from document.getElementById("game-logs"), but there is no element with id="game-logs" anywhere in index.html. Every addLog() call silently no-ops after the null check, so the log panel never renders.
const logBoxEl = document.getElementById("game-logs"); // → null always
Fix: Add <div id="game-logs"></div> to the HTML, or remove the log system entirely if unused.
Bug
Hukum suit selector only shows suits the player holds in their first 5 cards
In showHukumSelectionOverlay(), buttons for suits the player does not hold in their current 5-card hand are disabled. But in real Mendikot the player freely declares any suit — the restriction is a house rule not part of the standard game and can leave the player with no valid choice if all four suits appear in those 5 cards (paradoxically all buttons enabled) or edge-case disabled states.
btn.disabled = true; // disables suits not in the 5-card hand
Fix: Either remove the restriction, or at minimum clearly label why buttons are disabled so it doesn't feel like a UI glitch.
Bug
animateDealtCards() is defined but never called
The function exists in script.js but has no call site. It calls renderPlayerHand() and updatePlayerCardCountsHUD() with no arguments, which was likely an earlier version of the dealing logic before it was replaced by the async staggered engine — it's dead code.
Fix: Remove animateDealtCards() to avoid confusion and keep the codebase clean.
Bug
Crimson theme uses CSS filter on the board container, distorting UI widgets inside it
The theme-crimson class applies filter: hue-rotate(305deg) saturate(1.2) brightness(0.85) to #board-container. This filter also affects all child elements — player avatars, the HUD, card faces, score badges — turning them greenish/discoloured. CSS filter creates a new stacking context and cannot be "escaped" by children.
#board-container.theme-crimson { filter: hue-rotate(305deg) ... } /* affects all children */
Fix: Instead of a filter, use a dedicated crimson board image (board_cyber.png exists unused) or overlay a translucent crimson ::before pseudo-element so card faces and UI remain unaffected.
Bug
Race condition: aiTimer can trigger after game exits
state.aiTimer = setTimeout(triggerAILogicalPlay, 600) is set in multiple places, but restartToMenu() only clears the timer if the gameover overlay is visible. If the user somehow navigates away mid-trick, the pending setTimeout will fire and mutate a reset state object. triggerAILogicalPlay guards with if (!state.gameActive) return, but evaluateTrickWinner and startTrickCycle do not.
Fix: Clear all timers centrally in restartToMenu() and add if (!state.gameActive) return guards at the top of evaluateTrickWinner and startTrickCycle.
Logic errors — incorrect game rules or broken game-flow
Logic
Dealer rotation logic is inverted
In endGameRound(), the deal passes to the next player only when the dealer's team loses. In standard Mendikot, the deal always rotates to the next player clockwise each round, regardless of who wins. The current logic keeps the deal when the dealer's team wins, which is incorrect.
if (dealerTeam !== winningTeam) { state.dealer = (state.dealer + 1) % 4; }
Fix: Always rotate the dealer: state.dealer = (state.dealer + 1) % 4; unconditionally at the end of each round.
Logic
isPartnerWinning() uses the wrong partner index
The function computes partnerIdx = (state.turn + 2) % 4, which is the partner of whoever is currently playing (state.turn). But the function is called during an AI's turn to check if that AI's partner is winning. Since state.turn equals the current AI player, (turn + 2) % 4 is actually correct — however, the function is also used inside chooseAICard(playerIdx) where playerIdx is passed but not used in the partner calculation. If state.turn has already been advanced before this call, the result is wrong.
Fix: Pass playerIdx explicitly: const partnerIdx = (playerIdx + 2) % 4; and compare bestPlay.player === partnerIdx.
Logic
Open Hukum mode: AI cuts with any off-suit card even when it has the lead suit
In chooseAICard(), the Open Hukum branch is only reached when the AI cannot follow suit. But the logic re-checks the "best suit to cut with" and ignores that once Hukum is set, it should play trump strategically, not just to set Hukum again. After Hukum is revealed in open mode, state.hukum.revealed becomes true, but the earlier trump-cut branch may not fire correctly for the second+ tricks.
Fix: Restructure the AI cut decision: first check if state.hukum.revealed, and if so use the trump logic. Only run the "choose best suit to cut" logic when Hukum has not yet been set.
Logic
compareTwoCards() returns wrong result when neither card is trump or lead suit
When both cards are off-suit (neither trump nor lead suit), the function returns cardA.value - cardB.value. But a higher off-suit card should never beat a lead-suit card — the comparison should always return negative (losing) for any off-suit card vs a lead-suit card. The current code only handles one direction of the lead-suit check.
// Missing: if neither card follows lead suit, off-suit high card should not win
Fix: Add a check — if cardA is neither trump nor lead suit, it should automatically lose to any lead-suit card regardless of value.
Logic
Tie-breaker for 2-2 Mendis uses trick count but Mendikot rules use a re-deal
In endGameRound(), a 2-2 Mendi tie is resolved by whichever team won more tricks. Standard Mendikot rules say a 2-2 tie results in a draw (no winner) and the next game carries a "one up" — it does not resolve by trick count. This gives an incorrect win/loss outcome.
Fix: On a 2-2 tie, display "Draw — next game is a double!" rather than declaring a winner, or add a toggle for house rules.
UX issues — confusing or broken user experience
UX
No visual feedback when the player tries to click a card out of turn
When it is not the player's turn, pHandEl.classList.add("not-my-turn") dims the cards and disables pointer events. But there is no tooltip, shake animation, or message to explain why clicking does nothing — especially confusing for first-time players.
Fix: Add a brief shake animation or a toast message ("Wait for your turn") when the player taps a card during an AI turn.
UX
Hukum selection overlay can block the game permanently if dismissed accidentally
The #hukum-select-overlay has no close/cancel button. If the player clicks outside it (which has no handler), nothing happens. If a browser bug or extension interferes with the overlay, the game is stuck with no escape — the only fix is a full page refresh, losing all state.
Fix: Add a click-outside handler on the overlay that re-shows it or shows a warning, and/or add a "Cancel" button that resets to menu.
UX
board_cyber.png is loaded as an asset but never used in any theme
The file board_cyber.png exists in the game folder alongside board_green.png and board_royal.png, but the CSS only references the green and royal boards. The crimson theme re-uses the green board with a colour filter instead of the dedicated cyber board image.
Fix: Use board_cyber.png for the crimson/cyber theme and remove the problematic CSS filter hack.
UX
Mobile: cards overlap too aggressively with -30px negative margin on small screens
The hand uses margin-right: -30px on each .hand-card. With 13 cards and 76px card width, the total hand is only ~(76 + 12 × 46) = 628px — close to the 680px board width. On mobile or smaller viewports the cards become un-tappable. The board scales down via resizeBoard() but the card overlap isn't recalculated.
Fix: Compute negative margin dynamically based on hand count and available width, or reduce it further to -20px so cards remain distinguishable.
Performance issues
Perf
renderPlayerHand() rebuilds the entire DOM on every state change
pHandEl.innerHTML = "" followed by creating all card elements from scratch is called on every turn change, every card play, and after AI moves. With 13 cards, this creates and destroys ~65 DOM nodes on each call. It also re-attaches click listeners each time, and since the hand re-renders during the AI's turn it can interrupt in-progress CSS transitions.
Fix: Use DOM diffing — only remove the played card element and update unplayable / not-my-turn classes in place, rather than rebuilding the whole hand.
Perf
getRelativePos() forces layout reflow inside the dealing loop
dealCardsStaggered() attempts to pre-cache positions, but getRelativePos() calls getBoundingClientRect() which forces a synchronous layout. The cache is built once before the loop — which is good — but animateSingleCardDeal() still calls document.getElementById("board-container") and reads .getBoundingClientRect() inside the per-card callback, re-triggering layout on each of the 32 remaining-deal cards.
Fix: Pass the already-computed boardRect as part of cachedPositions and remove the redundant getBoundingClientRect() call inside animateSingleCardDeal().
